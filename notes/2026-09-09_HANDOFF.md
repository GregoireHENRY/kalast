## Decisions waiting on you

**1. Port the CPU thermophysical model to Rust?** The largest open item, and
the one that needs a call rather than a keyboard.

`heating.py` (471), `explicit.py` (362), `implicit.py` (345), `routine.py`
(201) and `nonuniform.py` (131) are 1,510 lines of numerics with **no call
into Rust between them**. `kalast.tpm.routine.step_conduction`, the inner step
of the model, is a Python function — `inspect.isfunction` says so.

So there are two thermophysical models: a GPU one in Rust and a CPU one in
numpy. Worth knowing when quoting the 23x: part of that gap is a language,
not the hardware. And the CPU path is the *reference the GPU path was
validated against* (1.5e-05 K), which is the code with the least excuse for
being in a different language from the engine.

Against doing it: `heating.py` carries the view-factor radiosity with a sparse
matvec per bounce, and `scipy.sparse` has no drop-in Rust equivalent. This is
not a weekend. It is also the one place where "Python is just a wrapper" is
currently untrue in a way that shows up in the physics rather than the
plumbing.

**2. Which stdout capture survives?** `kalast/editor.py:71 capture_output` and
`src/app/gui/mod.rs StdioCapture` do the same job for the same panel, and
since the Rust one is compiled out on Windows they behave differently by
platform. A log panel that captures different things on different machines is
a debugging tool that lies.

Two ways out, and they point opposite ways:

- Port the Rust capture to Windows. But Windows has no `dup2` on descriptor 1,
  and `SetStdHandle` plus a CRT `_dup2` does not redirect what Rust's
  `println!` already holds nor what a Python extension writes through its own
  CRT, so it would capture some output and silently miss the rest.
- Keep the Python one as the only implementation. Simple, works on both — and
  against the rule you just wrote down.

Not obvious, hence not decided. Mentioned in the audit note as the smallest of
the three findings and the most likely to bite.

**3. Does the Rust binary need to run `.py` scripts?** `cargo run --bin
kalast` opens the editor and handles `.rs` and `.obj` fully. Pressing Play on
a `.py` prints that the interpreter is needed and points at `python -m
kalast`. Embedding CPython in the binary would close that gap and would also
put a Python dependency back into a binary that was just freed of one.

  arbitrary colour, and `mesh.colors` with `color_modes[...] = 1` to mark a

And four things found while doing them:

- **The tree did not build on Windows at all.** `StdioCapture` uses
  `std::os::fd` and `libc::STDOUT_FILENO`; 22 errors, none related to the
  feature. Compiled out rather than ported, for the reason in decision 2.
- **The built-in colormaps were wrong.** Every one stopped short of t = 1 —
  viridis ended at its mid-green rather than its yellow, leaving the top
  quarter of every scale unreachable and the colour bar showing a ramp the

  than a 1920x1080 screen in both directions. Underneath it, `AppConfig`
  defaulted to a fixed 800x600 and the editor path to 2000x1300, and nothing
  set a window *position*, so on a two-monitor desktop the window centred
  across the join. All three now derive from the monitor: 70 % of it for a
  render window, 85 % with an editor, centred on one screen.
- **The Python bindings are now a cargo feature.** See below.

## The architecture rule, and the audit

You pointed out mid-session that the design is a Rust core with Python as a
wrapper, and that the editor loop living in `__main__.py` broke it. That is
now written down in `CLAUDE.md` ("Rust core, Python wrapper") with a
cross-reference from `notes/API.md`, and audited in
`notes/2026-09-09_rust_core_audit.md`.

Two of the three findings are fixed:

- `App::run_editor` is the engine's loop now, and both `python -m kalast` and
  `cargo run --bin kalast` call it. `__main__.py` is 46 lines. The seam is a
  `run_script` callback, because `exec` genuinely needs CPython — Rust owns
  the loop and calls out for the interpreter, rather than the reverse.
- `pyo3` is a feature, off by default, enabled by maturin. **`cargo run --bin
  kalast` opens the editor with Python removed from PATH entirely**, and
  `cargo test --lib` runs 40 tests without any PATH juggling — that last one
  fixes the `STATUS_DLL_NOT_FOUND` that made the suite look broken here.

The third is decision 2 above.

## Traps worth knowing before touching this

- **`#[pyfunction]` and `#[pymethods]` must be `cfg_attr`, not `cfg`.** The
  engine calls several of those functions itself, and gating the *item* rather
  than the attribute deletes them. Cost me a build.
- **Field attributes cannot be gated at all.** `#[pyclass]` expands before the
  `#[pyo3(get, set)]` on its own fields, so a `cfg_attr` there is still
  unexpanded when the class macro reads it. That is why `src/routines/` is
  gated as a whole module.
- **There are two config objects.** `AppConfig` holds the window size and the
  editor flag; `app.simulation.config` is the render config. Setting
  `app.simulation.config.editor = True` does *not* open the editor —
  `app.start_editor()` does. This produced a wrong measurement before I caught
  it.
- **Rebuilding needs the `.pyd` free.** VS Code's Jedi language server loads
  `kalast/_rs.pyd` for completions and holds it open, so `maturin develop`
  fails to copy. Find the holder rather than guessing:

      Get-Process | ? { $_.Modules.FileName -contains 'C:\projects\kalast\kalast\_rs.pyd' }

  It respawns, so killing it is safe.
